# Maeve 深度审查报告

> 日期：2026-11-15 · 范围：`:core` + `:app` 主源码（约 6.5 万行 Kotlin）+ 文档/构建/测试
> 方法：6 个只读审查维度并行（执行内核正确性 / 桥接与远程层 / 安全 / 质量与性能 / 测试 / 文档一致性），
> 全部结论经读码确认并附 file:line。严重度按 dev-standards：P0=会丢数据/可被利用/功能静默失效，P1=边界错误/泄漏/规范不符，P2=改进项。

## 0. 总览

工程质量整体偏高：AgentLoop 状态机主路径完整、压缩全程保持工具调用/结果配对、鉴权传输层（常量时间
Bearer 比较、Origin 403、失败冷却、relay TLS-only）扎实、测试文化强（4624 个单元测试、手写 Fake、
行为命名）。没有发现"确定性数据丢失/崩溃/死循环"。

但存在 **4 个 P0**：amoo 文件桥零鉴权、`phone_system_command` 零过滤零确认（两者叠加 = 能写信箱目录的
任何应用可拿到 uid 2000 shell）、`AgentLoop` 把模型调用失败错报成"步数上限"、`ActionEffects` 每次写
动作全量校验账本的热路径回退。另有约 20 个 P1，集中在取消/恢复窗口的状态卡死、SSRF、以及 SPEC 与实现
的系统性脱节（amoo 隐藏核心三处、MCP alias 契约未落地）。

| 维度 | 结论 |
|---|---|
| 执行内核 | 主路径健康；取消/排队窗口有 3 处可卡死 run 的 P1；1 处熔断可被绕过的 P1 |
| 桥接与远程 | 鉴权实现优秀；远程任务恢复路径有洞；文件桥无心跳 |
| 安全 | 文件桥与 system_command 是两个真实放大点（P0×2）；SSRF、明文 HTTP、沙箱桥为 P1 |
| 质量/性能 | 821 处 catch 无恶性静默吞；2 个 P0（错报+热路径）；大量 Regex/缓存可优化项 |
| 测试 | 通过率 98.7%（core）/97.3%（app），失败全是 Windows 平台假红；覆盖优秀，3 个高价值缺口 |
| 文档一致性 | 版本/包名/构建 pinned 全部属实；SPEC 的 amoo/MCP 契约与代码脱节；README Status 段失实 |

## 1. P0（必须修）

### P0-1 amoo 文件桥无来源鉴权：能写 `in/` 即可驱动整机

- 位置：`app/src/main/java/com/daiyimo/maeve/intercept/AmooBridge.kt:84,100-103`、`FileBridgeRequest.kt:27-28`、
  `task/RemoteTaskHub.kt:49`、`task/TaskService.kt:227`、`settings/FeatureFlags.kt:121`
- 现状：代码只做了 body≤16KiB、goal≤4000、ID 正则、重复键拒绝、幂等回执、并发上限；**SPEC §6.9 自己
  列出的"来源目录权限检查"未实现**。任何有 `/sdcard` 写权限的应用（或 adb）写
  `in/x.json={"goal":"用 phone_system_command 执行 …"}`，Maeve 即以 `RunOrigin.Mcp` 起任务执行，
  结果写回 `out/x.json` 供同一攻击者读取。
- 影响：信箱等价于"动手机的完整能力"交给任何能写该目录者；叠加 P0-2 即任意 sh 执行。
- 建议：信箱移入 App 私有目录 + `content://` 授予；或 `in/` 放只有 Maeve 能写的 nonce 文件要求请求
  携带；远程/Channel 来源不注册 `Verb.PhoneCommand`/`Verb.RootCommand`。

### P0-2 `phone_system_command`：模型可控字符串原样进 `sh -c`，无过滤、无确认、对所有来源开放

- 位置：`core/src/main/kotlin/com/daiyimo/maeve/core/cap/phone/PhoneAdvancedTools.kt:318-331`、
  `app/src/main/java/com/daiyimo/maeve/cap/phone/shell/ShellService.kt:1382-1387,1409-1414`、
  `core/src/main/kotlin/com/daiyimo/maeve/core/assembly/RunAssembler.kt:31-35`、`PhoneGroup.kt:19`、
  `app/src/main/assets/sandbox/maeve:29-33`
- 现状：`ProcessBuilder("/system/bin/sh","-c",command)` 之前只查长度。同为高危的 root 命令反而
  fail-closed 分类 + 单次确认（`RootCommandClass.classify`、`RootGroup.kt:62-69`），**shell 这条路径
  是全库最大的非对称**。`RunAssembler` 的 Unattended 裁剪只过滤 5 个 verb，`PhoneCommand` 不在其中；
  沙箱桥 `sandboxCallable=true` 让沙箱内下载的脚本可直接调用。
- 触发：沙箱脚本 CLI 一行调用 / 网页注入诱导模型 / 无人值守远程任务。
- 建议（至少三选一）：给 `Verb.PhoneCommand` 声明 `approvalRisk`（非只读即问）；壳层最小黑名单
  （`su`/`pm install`/`cmd`/`settings put`/重定向到解释器）；无人值守/远程来源不注册该工具，沙箱桥禁用。

### P0-3 `AgentLoop` 收尾轮把模型调用失败报成"步数上限"

- 位置：`core/src/main/kotlin/com/daiyimo/maeve/core/agent/AgentLoop.kt:963-968`
- 现状：`finalTurn` 的 `catch (e: Exception) { return StopRules.stepLimit(maxSteps) }`，而主循环
  472/489 行用 `StopRules.modelFailed(e)`（会把 Auth/Quota/Network 翻成具体人话）。
- 影响：API Key 无效、断网、限流在收尾轮发生时，用户看到"已达到 60 步上限"——事实错误且无法自助排查；
  eval 会把模型/网络问题归因成步数预算。
- 建议：改为 `return StopRules.modelFailed(e)`，与主循环一致。

### P0-4 `ActionEffects` 每次写动作全量校验执行账本（热路径随对话变长线性劣化）

- 位置：`core/src/main/kotlin/com/daiyimo/maeve/core/action/ActionEffects.kt:42-47`，调用点 `:57`(begin)/`:74`(settle)，
  触发点 `core/action/ActionExecutor.kt:233-234`
- 现状：`check(journal.receipts.all { … it.parametersDigest.matches(Regex("[a-f0-9]{64}")) … })`，
  `MAX_RECEIPTS=4096`；每次写动作 = 2 次全量文件读 + 2 次全量 JSON 反序列化 + 最多 8192 次 Regex 编译
  （正则每次匹配现场编译）。
- 建议：`private val DIGEST = Regex("[a-f0-9]{64}")` 提到 companion（一行修复）；全量重读属幂等设计，
  可另行评估改增量。

## 2. P1 — 正确性（执行内核 / 远程层）

1. **熔断可被交替回复绕过**：`AgentLoop.kt:520-536,573-574`，`emptyNudged/leakNudged` 在"漏工具调用/
   空回复 → 真调用"之间被重置，`maxSteps=Int.MAX_VALUE` 时无上界，退化为持续烧 token 的循环。
   建议改为任务级一次性标志，或连续 N 次空/漏回复强制终止。
2. **取消落在"出队已登记、协程未执行"窗口 → run 永久卡 running**：`TaskRun.kt:271-275` job setter 对
   `cancelRequested` 已置位的 job 直接 `cancel()`，协程体从不执行，`execute()` 的 finally 与
   `onRunEnded()` 都不跑 → run 永远在 `center.running()`、`taskState._busy` 卡死，同对话后续任务被拒，
   只有杀进程能恢复。建议协程入口检查 `cancelRequested` 并照常收尾。
3. **`cancelInput` 借 `CompletableDeferred.cancel()` 取消整个运行协程**：`UserExchange.kt:87-93` +
   `AgentLoop.kt:323`，插话取代旧提问时运行记录记成"任务异常中断"且绕过 `closeUnlessSteered()` 语义。
   建议用独立作废信号。
4. **`RunHandle.await()` 在 scope 取消后悬挂**：`RunHandle.kt:36-68`，`launch{}` 未得到调度时 `done`
   既未 complete 也未 completeExceptionally。建议 `job.invokeOnCompletion` 兜底。
5. **远程任务"claimed 但从未开跑"永久卡 `starting`**：`RemoteTaskHub.kt:114-124` 的 LOST 补救带
   `onlyUnclaimed=true`，对已认领行更新失败；`claimStart` 后 `begin()` 提前返回/异常/进程死亡即触发。
   远端 `maeve_wait_task` 只能干等超时。建议 LOST 分支去掉 `onlyUnclaimed`（`live(id)==null` 即等价于
   从未开跑）。
6. **`answer()` 在收件箱拒收时仍上报 accepted=true**：`RemoteTaskHub.kt:84-89` + `TaskRun.kt:345-351`，
   `tooLate` 是空 lambda，客户端认为回答已接受，实际 Agent 永远等不到。建议回传 `InputReceipt`。
7. **`TaskService.onRunEnded` 无兜底**：`TaskService.kt:479-528`，其中 `store.newConversation()` 做文件
   IO，抛异常同样导致 run 无法移出 running、busy 卡死。建议包一层 try/catch。
8. **amoo 文件桥无进度心跳**：`AmooBridge.kt:145-163`，out/ 从启动起就是同一份 `running`，amoo 侧无法
   区分"在推进"和"已卡死"（SPEC §12.3 记载的真机 4 分钟放弃现象即此）。SPEC §13.8/ADR-05 的 v3 心跳
   未落地。建议每 1.5s 原子刷新带 `step`/`updated_at`/`progress_note`。

## 3. P1 — 安全

1. **内置浏览器导航不拦内网/回环 → SSRF 读口**：`core/cap/web/WebUrlPolicy.kt:27-35` 只校验 scheme；
   `WebTabPool.kt:104-105`、`WebTab.kt:186-198` 对 `location=http://192.168.1.1/` 放行。而同项目
   `DownloadAddressPolicy.kt:17-21` 对下载却拦 localback/私网——导航侧没有等价规则。攻击者页面可把
   LAN 拓扑/路由器页面读进任务答案。建议主文档导航套用 `blockedHost`。
2. **局域网监听全程明文 HTTP**：`core/remote/HttpServer.kt:44-46`，Bearer 令牌同网段可嗅探后完整接管
   （含 P0-2 的 shell）。relay 出路反而是 TLS-only。建议首次 pairing 走 TLS/短期令牌，文档明示风险。
3. **沙箱→手机桥把 Write 级工具全开放**：`core/cap/sandbox/SandboxTools.kt:186-199` + `PhoneGroup.kt:19`，
   桥只校验 uid + 一次性 token，而 token 经环境变量 `MAEVE_TOKEN` 交给沙箱内任意进程
   （`ProcRunner.kt:56`）。PRoot/断网隔离被单向击穿。建议桥白名单缩到只读/低危。
4. **IrreversibleDetector 词表可被"无名元素 + 坐标点击 + 不写 target"稳定绕过**：
   `core/gate/IrreversibleDetector.kt:285-303`，无 text/resourceId 的图标按钮点击无命中依据即放行。
   建议坐标点击解析不到带名元素时按 `ActionRisk.Unknown` 走询问。
5. **USB 启动脚本一次性口令 TTL 24h**：`core/shell/HelperHandoff.kt:93-120,283`，`usb-start.sh` 里明文
   nonce 在 TTL 内始终有效，可读该文件者能让助手以 shell 身份起来并交接 Binder。建议缩短 TTL 或改为
   现取。

## 4. P1 — 质量与性能

1. `LeakedToolCall.kt:31`：每步对全部工具名（60-120 个）各编译一个 Regex；调用点 `AgentLoop.kt:529`。
   建议按名缓存或改 `indexOf` + 边界判断。
2. `ActionEffects.kt:117,126`：底层异常被换成无 cause 无日志的 `Blocked("effect_receipts_unavailable")`；
   `:127-132` 把 `action()` 内任何异常统一改成 `Blocked("effect_unknown")`。建议 `initCause` 或记日志。
3. `ModelCaller.kt:171`：每步全量重算 systemPrompt + specs 的 token 估算（约百 KB 文本），实际只在
   工具组展开时变。建议按 (systemPrompt, specs) 缓存。
4. `core/uistate/ScreenMap.kt:36-40`：每行 OCR 全量扫节点 + 排序，O(行数×节点数) 且每行新建两个
   List；密屏下每次读屏约 8000 次 covers + 80 次分配。建议按 layer 预分组。
5. `ShellService.kt:585`：每次 `startOwnPage` 做一次 `getPackagesForUid` PackageManager IPC，而同文件
   `:865` 已有 `ownPackages by lazy` 先例。建议复用。
6. `ShellService.kt:207`：反射 `Field` 在 lambda 内逐元素查找，同文件 337/361/966 都已外提，207 漏了。
7. 观测层失败完全无声：`AgentLoop.kt:1021-1028`（record{}）、`core/run/RunEventBus.kt:21,29` 空 catch；
   指标 sink 坏掉时运行记录不留痕迹。建议首个失败记一条 `Log.w`。
8. `AgentLoop.kt:406`：`installedApps` 失败静默降级为空列表，直接削弱知识匹配与渠道判断。建议 emit 一条
   `RunEvent.State`。
9. `AndroidScreen.kt:678-694`：`pasteUnseen` 内 `Thread.sleep` 轮询且持 `clipLock`（跑在 Dispatchers.IO）。
   建议改 `delay`。
10. `ShellService.kt:489`：catch 回退路径 `intent.action!!`，组件解析失败且 intent 无 action 时 NPE 且
    发生在 catch 块内。建议 `intent.action ?: return START_ERROR`。
11. `!!` 275 处，跨 `:core↔:app` 平台类型边界集中（ShellService 反射 13 处、WebScreen taskId 10 处、
    SandboxTools 8 处）。当前多被外层兜住，建议对反射结果统一 `as? T ?: throw`。
